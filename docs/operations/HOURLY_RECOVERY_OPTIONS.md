# 小时采集漏跑补偿方案

状态日期：2026-07-16  
当前结论：正式定时运行已出现超过120分钟、最高约206分钟的间隔；主采集任务本身成功，但GitHub托管定时器不保证准点。

## 方案A：继续接受GitHub定时器的尽力而为

做法：保留`17 * * * *`，只监控缺口，不补跑。

优点：最简单，不增加重复运行风险。  
缺点：可能连续漏掉1—3个小时；若来源页面短期更新并快速下沉，会延迟发现。

适合：只要求每天多次采集，不要求接近小时级连续性。

## 方案B：启用带守卫的30分钟恢复检查（推荐）

做法：每30分钟检查一次`Crawl policy sources hourly`最近成功的正式定时运行。只有最近成功运行距当前超过80分钟时，才执行一次恢复采集；否则立即结束。

已实现：

- `scripts/evaluate-hourly-recovery.mjs`；
- `.github/workflows/recover-policy-collection.yml`；
- 最近运行抑制、超时恢复和显式强制的自动测试；
- 恢复采集仍保持`manual-selection-only`、自动分析为0；
- 恢复工作流与主工作流使用不同并发组，但恢复守卫会避免正常情况下重复执行。

当前状态：工作流仅支持手工触发，尚未启用`schedule`。

优点：不依赖付费服务，能把多数调度缺口压缩到约80—110分钟。  
缺点：仍使用GitHub Actions，本身也可能排队；会增加少量运行次数；24小时正式验收仍只统计主工作流`schedule`，恢复运行只能作为业务连续性补偿，不能掩盖原定时器缺口。

## 方案C：迁移到外部可靠调度器

可选Supabase Cron、云函数、服务器计划任务或其他外部调度服务。

优点：可以获得更严格的调度控制和重试。  
缺点：增加部署、权限、成本和故障面；当前项目尚未证明需要该复杂度。

## 建议裁决

建议选择方案B：在24小时正式验收结论确认“调度连续性失败”后，为恢复工作流增加：

```yaml
schedule:
  - cron: "*/30 * * * *"
```

阈值保持80分钟。恢复工作流不得计入正式小时验收次数；7天验收同时分别报告“主调度连续性”和“业务采集连续性”。
