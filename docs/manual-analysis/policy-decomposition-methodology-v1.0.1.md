# 政策拆分与产业影响分析方法论 v1.0.1

## 一、方法论定位

本方法论是“政策产业影响终端”的核心分析内核，用来回答一份政策进入系统后到底应当如何被拆解、解释和展示。

它不是写作模板，也不是简单摘要规则，而是规定：

1. 政策先分型，再分析；
2. 先拆政策动作，再拆产业影响；
3. 先判断传导机制，再映射公司；
4. 先确认弱证据边界，再输出前端展示；
5. 不适合公司映射的政策，应允许只做政策结构化分析。

本方法论服务于三个目标：

- 避免把政策分析写成普通摘要；
- 避免把产业链相关误写成确定受益；
- 让不同政策之间可以比较、复核和持续迭代。

### v1.0.1 相比 v1.0 的补强点

本版补充五个关键判断层：

1. 区分“外壳类型”和“实质类型”；
2. 区分“政策信号强度”和“落地确定性”；
3. 区分“政策动作证据”“产业节点证据”和“公司映射证据”；
4. 增加分析深度分层 L0—L5；
5. 增加监管政策中“受约束方”和“合规服务方”的拆分。

这些补强点用于把方法论从“人工总纲”推进为“可结构化、可校验、可前端展示”的系统规则。

## 二、总流程

一份政策进入系统后，必须按以下顺序处理：

```text
政策原文
→ 外壳类型与实质类型识别
→ 政策信号强度与落地确定性判断
→ 分析深度分层
→ 政策动作拆分
→ 影响对象识别
→ 产业传导路径拆分
→ 分层证据等级判定
→ 公司映射边界判断
→ 后续验证清单生成
→ 前端可信展示
```

任何报告不得跳过“政策类型识别”和“政策动作拆分”直接进入公司映射。

## 三、第一步：政策类型识别

不同类型政策的拆法不同，不能用同一种报告模板机械处理。

### 1. 外壳类型与实质类型

现实政策经常存在标题外壳和实质内容不一致的情况。

例如：

- “国务院关于印发某规划的通知”：外壳类型是通知，实质类型是规划；
- “关于开展某专项行动的通知”：外壳类型是通知，实质类型是行动方案或专项行动；
- “关于同意某方案的批复”：外壳类型是批复，实质分析对象可能是被批复方案。

因此，系统应区分三个字段：

```json
{
  "documentShellType": "通知 | 批复 | 公告 | 意见 | 办法 | 条例 | 规划 | 方案",
  "substantivePolicyType": "规划 | 行动方案 | 实施意见 | 申报通知 | 名单目录 | 监管约束 | 资金支持 | 试点示范",
  "primaryActionType": "目标设定 | 任务部署 | 项目建设 | 资金支持 | 试点示范 | 标准约束 | 市场机制 | 名单认定 | 监管处罚 | 数据平台 | 地方责任"
}
```

后续分析以 `substantivePolicyType` 为主，而不是只看标题外壳。

### 2. 规划型政策

典型标题：

- “十五五”规划；
- 中长期规划；
- 建设规划；
- 发展规划。

主要特征：

- 指方向；
- 定目标；
- 分任务；
- 多数不直接产生订单；
- 通常需要地方实施方案、项目库、财政预算和配套细则验证。

分析口径：

- 可以拆产业方向；
- 可以拆任务链条；
- 公司映射必须降级；
- 不得写成确定受益。

### 3. 行动方案型政策

典型标题：

- 行动方案；
- 专项行动；
- 三年行动；
- 攻坚行动。

主要特征：

- 比规划更具体；
- 往往有时间表和任务清单；
- 可能带动项目、试点、标准或监管。

分析口径：

- 可重点拆“行动任务—牵头部门—实施对象—验证文件”；
- 若有数量目标、项目清单、资金安排，可适度提高政策动作证据等级；
- 没有名单和资金时仍不得直接映射确定公司。

### 4. 实施意见型政策

典型标题：

- 实施意见；
- 指导意见；
- 若干意见。

主要特征：

- 介于规划和执行文件之间；
- 常规定场景、机制、责任和支持方式；
- 可能形成后续试点、项目和地方细则。

分析口径：

- 重点拆“机制”和“场景”；
- 公司映射以平台、系统、服务和基础设施为主；
- 证据强度通常为间接证据，除非政策点名主体。

### 5. 通知型政策

典型标题：

- 关于开展……的通知；
- 关于组织申报……的通知；
- 关于印发……的通知。

主要特征：

- 可能只是转发文件；
- 也可能是具体申报、试点、任务布置。

分析口径：

- 先判断通知本身是否有实质动作；
- 若只是印发附件，重点分析附件；
- 若是申报通知，重点拆申报对象、条件、材料、资金和时间节点。

### 6. 公告目录型政策

典型标题：

- 公告；
- 名单；
- 目录；
- 入围名单；
- 认定结果。

主要特征：

- 通常最接近具体主体；
- 可能出现企业、项目、产品、设备或标准清单。

分析口径：

- 若企业或产品被列入名单，可作为强公司映射证据；
- 公司映射可以更明确，但仍不等于投资建议；
- 前端应显示“官方列示/名单证据”。

### 7. 批复型政策

典型标题：

- 国务院关于……的批复；
- 关于同意……的批复。

主要特征：

- 通常确认某规划、方案或事项；
- 批复文本本身可能信息很少；
- 真正可分析内容常在被批复文件中。

分析口径：

- 若缺少被批复正文，不宜强行深拆；
- 可做“政策入口卡”；
- 公司映射一般应谨慎或不做。

### 8. 监管约束型政策

典型标题：

- 办法；
- 条例；
- 规范；
- 裁量基准；
- 监管要求。

主要特征：

- 设置规则、门槛、处罚、标准或合规义务；
- 影响不一定是利好，可能是约束、成本或行业出清。

分析口径：

- 优先拆约束对象、合规成本、禁止事项和处罚机制；
- 公司映射应区分“受约束方”和“合规服务提供方”；
- 不得把监管趋严简单写成受益。

## 四、第二步：政策信号强度与落地确定性

v1.0 中“政策强度”容易混合两个不同问题：

1. 政策信号强不强；
2. 落地确定性高不高。

v1.0.1 将其拆成两个维度。

### 1. 政策信号强度 policySignalStrength

回答：这份政策在方向上重要吗？

| 等级 | 特征 |
|---|---|
| high | 中央或国务院层级、跨部门重点政策、明确国家战略方向、涉及重大产业或制度安排 |
| medium | 部门层面专项政策、行业重点任务、地方或领域性政策信号较明确 |
| low | 原则性表述、常规工作安排、信息披露或转发性文件 |

### 2. 落地确定性 implementationCertainty

回答：这份政策能否形成可验证的项目、资金、名单、规则或约束？

| 等级 | 特征 |
|---|---|
| high | 有资金、项目清单、试点名单、申报条件、强制标准、处罚机制、验收机制之一 |
| medium | 有明确任务、时间表、责任分工，但缺少资金、项目、名单或强制约束 |
| low | 只有方向、原则、倡议或宏观表述，缺少执行抓手 |

### 3. 两个维度不能互相替代

例如：

- 国务院规划：政策信号可能 high，但落地确定性可能 medium；
- 试点名单：政策信号可能 medium，但主体证据和落地确定性可能 high；
- 监管处罚规则：政策信号未必最高，但约束确定性可能 high；
- 批复但无正文：政策信号可能 medium，但可分析确定性可能 low。

建议报告字段：

```json
{
  "policySignalStrength": "high | medium | low",
  "implementationCertainty": "high | medium | low"
}
```

## 五、第三步：分析深度分层

不是所有政策都应该完整深拆到公司。系统应先判断分析深度。

| 层级 | 名称 | 输出深度 | 适用情况 |
|---|---|---|---|
| L0 | 只入库 | 仅保存原文和基础信息 | 文本太短、重复、无实质内容 |
| L1 | 政策速读 | 标题、摘要、发布机关、基本判断 | 批复入口、纯行政通知、无产业链政策 |
| L2 | 政策动作拆分 | actions、clauses、政策类型、强度判断 | 有任务但产业链不明确 |
| L3 | 产业链影响拆分 | chainNodes、chainEdges、后续验证清单 | 有明确产业链或制度传导 |
| L4 | 公司映射 | companies、公司证据等级、映射边界 | 有可解释产业环节，且不会误导 |
| L5 | 持续跟踪与横向对比 | compareInsights、后续验证、历史比较 | 有连续政策链条或需要长期跟踪 |

默认原则：

- 规划类政策通常最多到 L3，谨慎进入 L4；
- 公告目录和名单型政策可进入 L4；
- 资金申报、试点示范、项目建设类政策可进入 L4/L5；
- 批复无正文、纯行政事项、社会治理类政策通常停留在 L1/L2；
- 强行映射公司会误导时，不得进入 L4。

建议报告字段：

```json
{
  "analysisDepth": "L0 | L1 | L2 | L3 | L4 | L5",
  "analysisDepthReason": "为什么选择这个深度"
}
```

## 六、第四步：政策动作拆分

每份政策应拆成“政策动作”，而不是简单摘段。

政策动作包括：

| 动作类型 | 含义 | 常见产业影响 |
|---|---|---|
| 目标设定 | 给出数量、时间或阶段目标 | 形成中长期方向，但不直接形成订单 |
| 任务部署 | 要求部门或地方推进事项 | 需要后续实施方案验证 |
| 项目建设 | 明确建设工程、平台、基地、系统 | 可能形成项目和采购 |
| 资金支持 | 明确财政、基金、补贴、专项债 | 可能提高兑现概率 |
| 试点示范 | 设立试点、示范区、样板工程 | 关注试点名单和地方文件 |
| 标准约束 | 制定标准、规范、门槛 | 影响设备、服务和合规成本 |
| 市场机制 | 建立价格、交易、碳市场、数据市场等 | 影响商业模式和交易服务 |
| 名单认定 | 发布企业、项目、产品、设备名单 | 可作为强证据 |
| 监管处罚 | 明确限制、处罚、检查 | 影响合规成本和行业出清 |
| 数据平台 | 建设数据系统、数据库、信息平台 | 影响软件、数据治理和安全 |
| 地方责任 | 要求地方落实、考核、报送 | 后续看地方项目和预算 |

报告中的 `actions` 必须体现这些动作类型。

建议动作字段：

```json
{
  "actionType": "目标设定 | 任务部署 | 项目建设 | 资金支持 | 试点示范 | 标准约束 | 市场机制 | 名单认定 | 监管处罚 | 数据平台 | 地方责任",
  "actionEvidenceLevel": "strong | indirect | pending",
  "implementationDependency": "后续需要什么文件或项目验证"
}
```

## 七、第五步：产业影响传导拆分

产业影响不能从政策关键词直接跳到公司，而要经过传导链。

标准传导链为：

```text
政策动作
→ 资源或约束变化
→ 受影响主体
→ 产业环节
→ 商业模式或成本变化
→ 可验证信号
```

例如，政策说“建设行业高质量数据集”，不能直接写“AI公司受益”。应先拆成：

```text
数据采集
→ 数据清洗
→ 数据标注
→ 质量测评
→ 数据安全
→ 模型训练
→ 行业应用
→ 数据资产化
```

每个环节再判断：

- 是否被政策直接提到；
- 是否有资金或项目；
- 是否有试点或名单；
- 是否能映射企业；
- 需要什么后续文件验证。

## 八、第六步：分层证据等级规则

证据等级必须分对象，不能把“政策动作强证据”自动传导成“公司强证据”。

### 1. 三类证据对象

| 证据对象 | 字段建议 | 含义 |
|---|---|---|
| 政策动作证据 | actionEvidenceLevel | 政策是否明确提出某个动作 |
| 产业节点证据 | industryNodeEvidenceLevel | 政策是否直接支撑某个产业环节 |
| 公司映射证据 | companyMappingEvidenceLevel / evidenceLevel | 政策是否直接支撑某个公司映射 |

### 2. strong 强证据

对公司映射而言，满足任一条件才可为 strong：

- 政策正文点名公司、机构、产品或项目；
- 附件名单列示；
- 明确资金、补贴或采购对象；
- 有明确项目清单且公司为项目主体；
- 有强制标准直接约束某类主体且公司明确属于该主体。

### 3. indirect 间接证据

对公司映射而言，满足以下特征：

- 政策明确提到产业环节；
- 公司业务与该环节相关；
- 但政策未点名公司；
- 无订单、无采购、无补贴、无名单。

### 4. pending 待验证

满足以下特征：

- 只是主题相关；
- 只是概念相关；
- 公司业务与政策之间需要多层传导；
- 需要后续项目或文件确认。

## 九、第七步：公司映射规则

公司映射必须最后做。只有完成政策动作和产业传导后，才能考虑公司。

### 1. 公司映射五级

| 层级 | 含义 | 证据等级 |
|---|---|---|
| policy_named | 政策点名或附件列示 | strong |
| direct_industry | 直接产业链环节 | indirect 或 strong |
| indirect_industry | 间接产业链环节 | indirect |
| thematic_only | 主题相关 | pending |
| watch_only | 低置信观察 | pending |

### 2. 不得映射公司的情况

以下情况应允许 `companies=[]`：

- 政策只是宏观表态；
- 政策是批复，但缺少正文；
- 政策是纯行政组织安排；
- 政策不涉及明确产业链；
- 政策只对机关内部流程产生影响；
- 政策只有社会治理意义，缺乏可商业化环节；
- 强行映射公司会造成误导。

### 3. 公司映射必须回答的问题

每个公司至少回答：

1. 为什么被纳入；
2. 属于哪个产业链环节；
3. 政策有没有点名；
4. 是否有订单、采购、补贴或名单证据；
5. 证据是强、间接还是待验证；
6. 后续需要什么验证；
7. 为什么不构成投资建议。

## 十、第八步：监管政策的特殊拆分

监管政策不能简单按“利好/受益”拆分，应区分两类主体。

### 1. 受约束方 constraint_exposed

含义：政策直接提高其合规成本、经营门槛、报告义务、处罚风险或淘汰压力。

常见影响：

- 合规成本上升；
- 产能受限；
- 违规处罚风险上升；
- 中小企业出清；
- 龙头企业可能相对受益，但必须拆分“成本”和“竞争格局”两面。

### 2. 合规服务方 compliance_provider

含义：为被监管主体提供检测、认证、审计、数据安全、系统建设、咨询、设备改造等服务。

常见影响：

- 检测认证需求；
- 安全合规系统；
- 数据治理；
- 节能降碳改造；
- 第三方审计咨询。

建议公司字段：

```json
{
  "regulatoryRole": "constraint_exposed | compliance_provider | mixed | not_applicable"
}
```

监管政策中不得把 `constraint_exposed` 简单写成 `beneficiary`。

## 十一、第九步：后续验证清单

每份报告都应生成后续验证清单。

常见验证项：

- 地方实施方案；
- 专项资金安排；
- 项目库；
- 试点名单；
- 示范名单；
- 招投标公告；
- 行业标准；
- 采购目录；
- 财政预算；
- 企业中标公告；
- 项目验收公告；
- 监管处罚案例；
- 统计指标发布。

如果一个产业影响没有后续验证项，说明它可能只是叙事，不适合高置信展示。

## 十二、第十步：前端展示规则

前端展示应跟随证据等级，不得只展示分数。

### 对 strong

可显示：

- 官方点名；
- 附件列示；
- 强证据。

仍需提示：不构成投资建议。

### 对 indirect

必须显示：

- 产业链相关；
- 未被政策点名；
- 无订单证据；
- 需等待项目或招标验证。

### 对 pending

必须弱化展示：

- 低置信观察；
- 主题相关；
- 待验证；
- 不宜进入主要公司卡片高亮区域。

## 十三、第十一步：哪些政策值得深拆

值得深拆的政策通常具备：

- 层级高；
- 全文充分；
- 任务明确；
- 有产业链；
- 有执行抓手；
- 有后续验证文件；
- 能形成前端结构化展示。

不值得深拆的政策通常具备：

- 文本太短；
- 只是批复入口；
- 只有名单但无产业解释价值；
- 纯行政流程；
- 缺少产业链；
- 强行公司映射会误导。

## 十四、报告生成前的六问

每次写报告前，必须先回答：

1. 这份政策的外壳类型和实质类型分别是什么？
2. 它的政策信号强度和落地确定性分别是什么？
3. 它应进入 L0—L5 哪个分析深度？
4. 它的实际政策动作是什么？
5. 它的产业传导路径是什么？
6. 它是否真的适合做公司映射？

如果第六问答案是否定，应明确写“本政策不适合公司映射”。

## 十五、与现有文件的关系

本方法论是上位规则。

- `policy-analysis-quality-standard-v1.1.md`：负责质量边界和发布标准；
- `report-template-v1.1.json`：负责报告字段结构；
- `validate-manual-report.mjs`：负责把部分质量规则自动化；
- 前端公司卡片和详情页：负责把证据边界展示给用户。

后续新增报告、回炉报告和前端优化，都应优先遵守本方法论。

## 十六、最终原则

政策解析终端不应成为“政策摘要 + 公司联想”的工具。

它应当成为：

```text
政策文本
→ 政策动作
→ 作用机制
→ 产业链节点
→ 证据等级
→ 影响边界
→ 后续验证
→ 可信展示
```

只有这条链条完整，报告才允许进入相应深度的发布流程。
