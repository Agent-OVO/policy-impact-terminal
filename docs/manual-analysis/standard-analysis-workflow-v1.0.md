# 政策分析标准作业流程 v1.0

## 一、目标

本流程用于规范每一次人工政策分析，确保报告不是临时发挥，而是稳定遵循：

```text
先分型
再拆动作
再拆产业传导
最后决定是否映射公司
发布前强制质量复核
```

本流程适用于：

- 新增政策报告；
- 旧报告回炉；
- 待分析政策筛选；
- 人工分析写回 Supabase 前的质量把关。

## 二、作业总流程

每次分析必须经过 8 个阶段：

```text
01 资料读取
02 政策分型
03 分析深度决策
04 政策动作拆分
05 产业传导拆分
06 公司映射决策
07 报告生成与自检
08 严格校验与发布
```

任何报告不得从“政策标题”直接跳到“公司清单”。

## 三、01 资料读取

### 必做事项

1. 读取政策标题、发布机关、发布日期、来源链接；
2. 读取完整政策正文；
3. 判断是否有附件、名单、表格、申报条件或项目清单；
4. 判断正文是否足够分析。

### 不合格情形

以下情形不得直接进入公司映射：

- 只有标题或摘要；
- 正文过短；
- 批复但缺少被批复文件；
- 只有新闻稿，没有政策正文；
- 只看到转载，未确认官方来源。

## 四、02 政策分型

必须同时判断三类字段：

```json
{
  "documentShellType": "外壳类型",
  "substantivePolicyType": "实质类型",
  "primaryActionType": "主要动作"
}
```

### 外壳类型

看文件表面形式，例如：通知、批复、公告、意见、办法、条例、规划、方案。

### 实质类型

看文件真正内容，例如：规划、行动方案、实施意见、申报通知、名单目录、监管约束、资金支持、试点示范。

### 主要动作

看政策实际做了什么，例如：目标设定、任务部署、项目建设、资金支持、试点示范、标准约束、市场机制、名单认定、监管处罚、数据平台、地方责任。

## 五、03 分析深度决策

必须先判断分析深度：

| 层级 | 名称 | 适用情况 |
|---|---|---|
| L0 | 只入库 | 文本太短、重复、无实质内容 |
| L1 | 政策速读 | 批复入口、纯行政通知、无产业链政策 |
| L2 | 政策动作拆分 | 有任务但产业链不明确 |
| L3 | 产业链影响拆分 | 有明确产业链或制度传导 |
| L4 | 公司映射 | 有可解释产业环节，且不会误导 |
| L5 | 持续跟踪与横向对比 | 有连续政策链条或长期验证价值 |

### 决策原则

- 不适合公司映射的政策，不得强行进入 L4；
- 规划类政策可进入 L3，进入 L4 必须降级表达；
- 名单目录、申报通知、资金支持、试点示范更适合进入 L4/L5；
- 批复无正文通常停留在 L1；
- 监管政策应重点拆约束和合规服务，不应简单写成受益。

## 六、04 政策动作拆分

每条 action 必须回答：

1. 政策动作是什么；
2. 动作类型是什么；
3. 政策是否明确提出该动作；
4. 需要什么后续文件验证。

建议字段：

```json
{
  "actionType": "项目建设",
  "actionEvidenceLevel": "strong",
  "implementationDependency": "等待项目库、资金安排或招投标公告"
}
```

### 动作不得写成公司结论

错误写法：

```text
该政策利好某公司。
```

正确写法：

```text
该政策提出建设某类平台，可能形成平台建设、数据治理和安全合规需求，后续需等待项目或采购公告验证。
```

## 七、05 产业传导拆分

产业传导必须经过以下链条：

```text
政策动作
→ 资源或约束变化
→ 受影响主体
→ 产业环节
→ 商业模式或成本变化
→ 可验证信号
```

每个产业节点必须有：

```json
{
  "industryNodeEvidenceLevel": "strong | indirect | pending",
  "verificationSignals": ["后续验证文件或项目"]
}
```

### 产业节点强，不等于公司强

政策明确提出“建设某平台”，可以说明该产业节点证据强。  
但如果政策没有点名某公司，则该公司的映射仍然通常是 indirect 或 pending。

## 八、06 公司映射决策

公司映射是最后一步，不是默认步骤。

### 允许公司映射的前提

同时满足：

1. 产业节点明确；
2. 公司业务与节点有可解释关系；
3. 不会让用户误以为政策点名或确定受益；
4. 已明确标注证据等级；
5. 已写清后续验证条件。

### 公司映射必须填写

```json
{
  "companyMappingEvidenceLevel": "strong | indirect | pending",
  "mappingLevel": "policy_named | direct_industry | indirect_industry | thematic_only | watch_only",
  "officialMention": false,
  "hasOrderEvidence": false,
  "hasSubsidyEvidence": false,
  "hasProcurementEvidence": false,
  "notInvestmentSignal": true,
  "implementationDependency": "后续验证条件"
}
```

### 禁止行为

- 不得把未点名公司写成确定受益；
- 不得把规划方向写成订单机会；
- 不得用高分掩盖低证据；
- 不得为了前端展示硬凑公司；
- 不得输出买入、目标价、推荐、收益承诺等投资化表达。

## 九、07 报告生成与自检

生成报告后，先人工自检：

1. 是否有 `methodologyVersion`；
2. 是否有外壳类型、实质类型、主要动作；
3. 是否有政策信号强度与落地确定性；
4. 是否有分析深度和深度理由；
5. actions 是否带 `actionType`；
6. chainNodes 是否带 `industryNodeEvidenceLevel`；
7. companies 是否带 `companyMappingEvidenceLevel`；
8. evidence 是否带 `evidenceObject`；
9. 证据摘录和人工解释是否分开；
10. 横向对比未启用时是否透明说明；
11. 是否写清“不构成投资建议”；
12. 是否生成后续验证清单。

## 十、08 严格校验与发布

发布前必须运行：

```bash
MANUAL_QUALITY_STRICT=true npm run manual:validate -- manual-reports/<policy-id>.json
```

通过后才允许触发：

```bash
gh workflow run apply-manual-analysis.yml -f policy_id=<policy-id> -f report_file=manual-reports/<policy-id>.json
```

发布成功后，必须确认日志包含：

```text
MANUAL_QUALITY_STRICT: true
manual:validate ok
published: true
```

## 十一、角色分工建议

### 分析者

负责政策阅读、动作拆分、产业传导和报告生成。

### 复核者

负责检查证据边界、公司映射、风险提示和校验结果。

### 发布者

负责执行严格校验、GitHub Actions apply、Supabase 写回和前端状态复核。

可以是同一个人，但三个角色的检查动作不能省略。

## 十二、最终标准

一份高质量报告必须做到：

```text
看得出政策类型
看得出政策动作
看得出产业传导
看得出证据边界
看得出为什么映射公司
看得出后续要验证什么
看不出荐股倾向
```
