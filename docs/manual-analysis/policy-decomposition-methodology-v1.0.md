# 政策拆分与产业影响分析方法论 v1.0

## 一、方法论定位

本方法论是“政策产业影响终端”的核心分析内核，用来回答一份政策进入系统后到底应当如何被拆解、解释和展示。

它不是写作模板，也不是简单摘要规则，而是规定：

1. 政策先分型，再分析；
2. 先拆政策动作，再拆产业影响；
3. 先判断传导机制，再映射公司；
4. 先确认弱证据边界，再输出前端展示；
5. 不适合公司映射的政策，应允许只做政策结构化分析。

本方法论服务于三个目标：

- 避免把政策分析写成普通摘要；
- 避免把产业链相关误写成确定受益；
- 让不同政策之间可以比较、复核和持续迭代。

## 二、总流程

一份政策进入系统后，必须按以下顺序处理：

```text
政策原文
→ 政策类型识别
→ 政策强度判断
→ 政策动作拆分
→ 影响对象识别
→ 产业传导路径拆分
→ 证据等级判定
→ 公司映射边界判断
→ 后续验证清单生成
→ 前端可信展示
```

任何报告不得跳过“政策类型识别”和“政策动作拆分”直接进入公司映射。

## 三、第一步：政策类型识别

不同类型政策的拆法不同，不能用同一种报告模板机械处理。

### 1. 规划型政策

典型标题：

- “十五五”规划；
- 中长期规划；
- 建设规划；
- 发展规划。

主要特征：

- 指方向；
- 定目标；
- 分任务；
- 多数不直接产生订单；
- 通常需要地方实施方案、项目库、财政预算和配套细则验证。

分析口径：

- 可以拆产业方向；
- 可以拆任务链条；
- 公司映射必须降级；
- 不得写成确定受益。

### 2. 行动方案型政策

典型标题：

- 行动方案；
- 专项行动；
- 三年行动；
- 攻坚行动。

主要特征：

- 比规划更具体；
- 往往有时间表和任务清单；
- 可能带动项目、试点、标准或监管。

分析口径：

- 可重点拆“行动任务—牵头部门—实施对象—验证文件”；
- 若有数量目标、项目清单、资金安排，可适度提高证据等级；
- 没有名单和资金时仍不得直接映射确定公司。

### 3. 实施意见型政策

典型标题：

- 实施意见；
- 指导意见；
- 若干意见。

主要特征：

- 介于规划和执行文件之间；
- 常规定场景、机制、责任和支持方式；
- 可能形成后续试点、项目和地方细则。

分析口径：

- 重点拆“机制”和“场景”；
- 公司映射以平台、系统、服务和基础设施为主；
- 证据强度通常为间接证据，除非政策点名主体。

### 4. 通知型政策

典型标题：

- 关于开展……的通知；
- 关于组织申报……的通知；
- 关于印发……的通知。

主要特征：

- 可能只是转发文件；
- 也可能是具体申报、试点、任务布置。

分析口径：

- 先判断通知本身是否有实质动作；
- 若只是印发附件，重点分析附件；
- 若是申报通知，重点拆申报对象、条件、材料、资金和时间节点。

### 5. 公告目录型政策

典型标题：

- 公告；
- 名单；
- 目录；
- 入围名单；
- 认定结果。

主要特征：

- 通常最接近具体主体；
- 可能出现企业、项目、产品、设备或标准清单。

分析口径：

- 若企业或产品被列入名单，可作为强证据；
- 公司映射可以更明确，但仍不等于投资建议；
- 前端应显示“官方列示/名单证据”。

### 6. 批复型政策

典型标题：

- 国务院关于……的批复；
- 关于同意……的批复。

主要特征：

- 通常确认某规划、方案或事项；
- 批复文本本身可能信息很少；
- 真正可分析内容常在被批复文件中。

分析口径：

- 若缺少被批复正文，不宜强行深拆；
- 可做“政策入口卡”；
- 公司映射一般应谨慎或不做。

### 7. 监管约束型政策

典型标题：

- 办法；
- 条例；
- 规范；
- 裁量基准；
- 监管要求。

主要特征：

- 设置规则、门槛、处罚、标准或合规义务；
- 影响不一定是利好，可能是约束、成本或行业出清。

分析口径：

- 优先拆约束对象、合规成本、禁止事项和处罚机制；
- 公司映射应区分“受约束方”和“合规服务提供方”；
- 不得把监管趋严简单写成受益。

## 四、第二步：政策强度判断

政策强度不是政策层级越高就一定越强，而是看其能否形成实际行动。

### 高强度政策

具备以下特征之一：

- 有明确资金安排；
- 有项目清单；
- 有试点名单；
- 有申报条件；
- 有强制标准；
- 有处罚机制；
- 有具体数量目标和时间表；
- 有明确责任部门和验收机制。

### 中强度政策

具备以下特征：

- 有明确任务方向；
- 有责任分工；
- 有阶段目标；
- 但缺少资金、项目、名单或强制约束。

### 低强度政策

具备以下特征：

- 主要是原则性表述；
- 内容偏宏观；
- 无执行抓手；
- 无明确项目、资金、名单、标准或处罚。

## 五、第三步：政策动作拆分

每份政策应拆成“政策动作”，而不是简单摘段。

政策动作包括：

| 动作类型 | 含义 | 常见产业影响 |
|---|---|---|
| 目标设定 | 给出数量、时间或阶段目标 | 形成中长期方向，但不直接形成订单 |
| 任务部署 | 要求部门或地方推进事项 | 需要后续实施方案验证 |
| 项目建设 | 明确建设工程、平台、基地、系统 | 可能形成项目和采购 |
| 资金支持 | 明确财政、基金、补贴、专项债 | 可能提高兑现概率 |
| 试点示范 | 设立试点、示范区、样板工程 | 关注试点名单和地方文件 |
| 标准约束 | 制定标准、规范、门槛 | 影响设备、服务和合规成本 |
| 市场机制 | 建立价格、交易、碳市场、数据市场等 | 影响商业模式和交易服务 |
| 名单认定 | 发布企业、项目、产品、设备名单 | 可作为强证据 |
| 监管处罚 | 明确限制、处罚、检查 | 影响合规成本和行业出清 |
| 数据平台 | 建设数据系统、数据库、信息平台 | 影响软件、数据治理和安全 |
| 地方责任 | 要求地方落实、考核、报送 | 后续看地方项目和预算 |

报告中的 `actions` 必须体现这些动作类型。

## 六、第四步：产业影响传导拆分

产业影响不能从政策关键词直接跳到公司，而要经过传导链。

标准传导链为：

```text
政策动作
→ 资源或约束变化
→ 受影响主体
→ 产业环节
→ 商业模式或成本变化
→ 可验证信号
```

例如，政策说“建设行业高质量数据集”，不能直接写“AI公司受益”。应先拆成：

```text
数据采集
→ 数据清洗
→ 数据标注
→ 质量测评
→ 数据安全
→ 模型训练
→ 行业应用
→ 数据资产化
```

每个环节再判断：

- 是否被政策直接提到；
- 是否有资金或项目；
- 是否有试点或名单；
- 是否能映射企业；
- 需要什么后续文件验证。

## 七、第五步：公司映射规则

公司映射必须最后做。只有完成政策动作和产业传导后，才能考虑公司。

### 公司映射五级

| 层级 | 含义 | 证据等级 |
|---|---|---|
| policy_named | 政策点名或附件列示 | strong |
| direct_industry | 直接产业链环节 | indirect 或 strong |
| indirect_industry | 间接产业链环节 | indirect |
| thematic_only | 主题相关 | pending |
| watch_only | 低置信观察 | pending |

### 不得映射公司的情况

以下情况应允许 `companies=[]`：

- 政策只是宏观表态；
- 政策是批复，但缺少正文；
- 政策是纯行政组织安排；
- 政策不涉及明确产业链；
- 政策只对机关内部流程产生影响；
- 政策只有社会治理意义，缺乏可商业化环节；
- 强行映射公司会造成误导。

### 公司映射必须回答的问题

每个公司至少回答：

1. 为什么被纳入；
2. 属于哪个产业链环节；
3. 政策有没有点名；
4. 是否有订单、采购、补贴或名单证据；
5. 证据是强、间接还是待验证；
6. 后续需要什么验证；
7. 为什么不构成投资建议。

## 八、第六步：证据等级规则

### strong 强证据

满足任一条件：

- 政策正文点名公司、机构、产品或项目；
- 附件名单列示；
- 明确资金、补贴或采购对象；
- 有明确项目清单；
- 有强制标准直接约束某类主体。

### indirect 间接证据

满足以下特征：

- 政策明确提到产业环节；
- 公司业务与该环节相关；
- 但政策未点名公司；
- 无订单、无采购、无补贴、无名单。

### pending 待验证

满足以下特征：

- 只是主题相关；
- 只是概念相关；
- 公司业务与政策之间需要多层传导；
- 需要后续项目或文件确认。

## 九、第七步：后续验证清单

每份报告都应生成后续验证清单。

常见验证项：

- 地方实施方案；
- 专项资金安排；
- 项目库；
- 试点名单；
- 示范名单；
- 招投标公告；
- 行业标准；
- 采购目录；
- 财政预算；
- 企业中标公告；
- 项目验收公告；
- 监管处罚案例；
- 统计指标发布。

如果一个产业影响没有后续验证项，说明它可能只是叙事，不适合高置信展示。

## 十、第八步：前端展示规则

前端展示应跟随证据等级，不得只展示分数。

### 对 strong

可显示：

- 官方点名；
- 附件列示；
- 强证据。

仍需提示：不构成投资建议。

### 对 indirect

必须显示：

- 产业链相关；
- 未被政策点名；
- 无订单证据；
- 需等待项目或招标验证。

### 对 pending

必须弱化展示：

- 低置信观察；
- 主题相关；
- 待验证；
- 不宜进入主要公司卡片高亮区域。

## 十一、第九步：哪些政策值得深拆

值得深拆的政策通常具备：

- 层级高；
- 全文充分；
- 任务明确；
- 有产业链；
- 有执行抓手；
- 有后续验证文件；
- 能形成前端结构化展示。

不值得深拆的政策通常具备：

- 文本太短；
- 只是批复入口；
- 只有名单但无产业解释价值；
- 纯行政流程；
- 缺少产业链；
- 强行公司映射会误导。

## 十二、报告生成前的三问

每次写报告前，必须先回答：

1. 这份政策属于什么类型？
2. 它的实际政策动作是什么？
3. 它是否真的适合做公司映射？

如果第三问答案是否定，应明确写“本政策不适合公司映射”。

## 十三、与现有文件的关系

本方法论是上位规则。

- `policy-analysis-quality-standard-v1.1.md`：负责质量边界和发布标准；
- `report-template-v1.1.json`：负责报告字段结构；
- `validate-manual-report.mjs`：负责把部分质量规则自动化；
- 前端公司卡片和详情页：负责把证据边界展示给用户。

后续新增报告、回炉报告和前端优化，都应优先遵守本方法论。

## 十四、最终原则

政策解析终端不应成为“政策摘要 + 公司联想”的工具。

它应当成为：

```text
政策文本
→ 政策动作
→ 作用机制
→ 产业链节点
→ 证据等级
→ 影响边界
→ 后续验证
→ 可信展示
```

只有这条链条完整，报告才允许发布。
