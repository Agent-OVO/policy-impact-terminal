# ADR-002 报告唯一事实源

状态：已接受
日期：2026年7月10日

## 背景

当前生产前端从`policies.metadata`读取整包报告，并兼容`reportPayload`、`policyReport`及多种历史别名；数据库同时存在尚未成为生产权威的规范化表。该模式已经发生过公司计数和权威映射漂移。

## 备选方案

### 方案A：版本化JSON为唯一事实源

优点是适应政策报告异质性、迁移成本低、版本和回滚直观。缺点是跨政策查询必须建立索引投影。

### 方案B：规范化关系表为唯一事实源

优点是SQL查询和约束强。缺点是完整报告表达高度异质，动态组装复杂，模式升级和历史回滚成本高，容易把展示性结构过度拆表。

### 方案C：分层不可变事实源与派生投影

将原文、完整报告和跨政策查询分别放在最适合的权威层，并用确定性投影连接。

## 决策

采用方案C：

1. **政策原文事实源**：不可变的政策原文版本，保存规范化原文、来源、获取时间、`source_document_hash`和段落索引；`policies`只保存当前原文版本指针和稳定身份。
2. **完整报告事实源**：`report_revisions.payload`中的不可变、版本化、通过模式校验的完整报告JSON。
3. **跨政策读模型**：按`revision_id`自动生成的公司、产业、政策网络、信号、证据和观察字段投影。

规范化投影不是第二套可人工维护的事实源。投影必须：

- 由指定报告修订自动生成；
- 带`revision_id`、投影版本和生成哈希；
- 与发布在同一事务中完成或明确保持未发布；
- 可从报告修订完全重建；
- 禁止绕过投影器人工双写。

## 为什么不是继续把数据塞进metadata

目标架构使用独立`report_revisions`表，具有主键、父修订、状态、模式版本、分析版本、内容哈希、原文哈希、作者、审核者和发布时间。`policies.metadata`只保留低风险扩展信息，不再承载完整报告、镜像报告、分析副本和重复计数。

## 读取规则

- 单报告详情读取`current_published_revision_id`对应的payload；
- 公司反查、产业聚合、时间线和观察池读取同一修订生成的投影；
- 列表计数从投影聚合，不从payload内重复维护的计数字段读取；
- 历史修订详情按明确的revision读取，不受当前指针变化影响。

## 一致性约束

发布前必须验证：

- payload模式与引用完整性；
- `content_hash`与实际payload一致；
- 投影记录全部指向同一revision；
- 投影摘要与payload确定性计算结果一致；
- 当前发布指针只能指向已发布且投影成功的修订。

## 后果

该方案保留JSON对异质报告的适应性，同时支持数百份政策后的SQL聚合、差量更新和回滚。代价是必须建设可靠投影器、事务发布和投影一致性测试。
