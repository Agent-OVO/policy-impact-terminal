# 零额外费用验证与部署策略 v1.0

日期：2026年7月11日。
状态：已接受，作为阶段七、阶段八后续工作的成本硬约束。

## 一、决策

政策产业影响终端后续建设不得为了验证、暂存或部署而新增任何额外付费资源。未经新的明确决策，不创建：

- Supabase Preview Branch；
- 新的付费Supabase项目；
- 独立付费数据库或云主机；
- 付费CI额度、付费监控或其他新增计费服务；
- 为本项目单独购买的模型、代理或测试调用额度。

既有生产项目、既有GitHub仓库和本地计算环境可以继续使用，但不得通过扩容、升级套餐或新增计费资源绕过本约束。

## 二、零费用验证层级

### 1. 仓库静态验证

持续执行：

- TypeScript和Deno类型检查；
- JSON、YAML、TOML解析；
- SQL对象、权限和契约静态检查；
- 工作流结构契约；
- 敏感信息和禁入路径检查；
- 报告内容哈希和确定性投影检查。

### 2. 本地真实PostgreSQL语义验证

使用固定版本`@electric-sql/pglite@0.5.4`在系统临时目录运行PostgreSQL WASM。依赖按次安装，测试完成后删除，不加入项目依赖或锁文件。

验证范围包括：

- 全部历史迁移顺序执行；
- 触发器、约束、RLS策略和授权对象；
- 报告发布、回滚、幂等和审计；
- Token预算预留和结算；
- 邀请、暂停、恢复、保留期清理和两阶段删除；
- 20份官方原文、修订和全部投影的批量装载；
- 重复装载幂等性；
- 使用真实数据库角色和JWT claim模拟进行表级RLS访问验证。

PGlite不等同于Supabase托管环境，因此不能证明GoTrue、PostgREST网关和Edge网关的全部行为，但它是零成本条件下的主要数据库执行门。

### 3. 既有生产项目只读核验

在不新增资源、不写生产数据的前提下，可以使用既有项目和已有管理员凭据执行：

- 生产Schema和迁移状态读取；
- 20份`full_text`只读导出；
- 生产原文与官方网页及附件复合原文差异报告；
- 当前Auth、profile、policy和报告数量审计；
- 当前备份能力、恢复入口和套餐事实核验。

只读凭据不得写入仓库、日志或本地长期明文文件。

### 4. 既有生产项目加法影子部署

只有满足以下全部条件，并再次获得明确生产部署授权后，才能在现有生产项目执行加法迁移：

1. 本地全部质量门通过；
2. 20份影子包`deploymentReady=true`；
3. 生产原文差异已人工处置；
4. 已确认现有套餐具备可用恢复点，或已经形成不增加费用的可恢复导出；
5. 目标project ref、数据库主机和迁移列表再次核对；
6. 迁移只增加对象，不切换旧前端和旧人工写回；
7. 生产装载完成后进行新旧双轨只读对照；
8. 发现异常时只停用新路径，不立即删除新表。

这一方式没有独立暂存隔离，因此风险高于Preview Branch。它只能作为零费用约束下的受控方案，不能降低备份、确认和回滚要求。

## 三、明确禁止的替代做法

不得因为没有付费暂存环境而：

- 直接在生产主库试错；
- 把PGlite通过表述为Supabase Auth、PostgREST或Edge集成已经通过；
- 绕过备份直接`supabase db push`；
- 将新前端或新写入链与数据库迁移同时切换；
- 暂时打开公共注册以方便测试；
- 使用service role密钥作为普通用户测试令牌；
- 删除旧`metadata`、旧mapper或旧写回路径。

## 四、剩余不可消除的不确定性

不创建真实Supabase隔离环境意味着，在生产影子部署前仍无法完全验证：

- Supabase Auth真实JWT和会话刷新行为；
- PostgREST对新增RPC、JSON和错误码的最终序列化；
- 托管RLS、service role和Edge网关的组合行为；
- 多个真实网络连接下的并发发布和预算争用；
- Auth Admin硬删除与数据库外键级联的托管实现差异。

这些不确定性必须在生产影子阶段以最小范围、可回滚方式验证，不能在文档中隐去。

## 五、执行顺序

零费用路线固定为：

```text
仓库封板
→ 本地PostgreSQL和RLS高保真测试
→ 既有生产只读差异核验
→ 确认现有备份/恢复能力
→ 再次取得生产加法迁移授权
→ 生产影子部署但不切换读写
→ 新旧双轨对照
→ 分阶段切换写入和读取
```

在生产影子部署获得授权前，所有新数据库和Edge能力保持“仓库生产候选、线上未部署”状态。
