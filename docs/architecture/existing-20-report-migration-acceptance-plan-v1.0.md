# 20份存量报告迁移验收方案 v1.0

状态：20份官方原文、真实影子迁移和临时PostgreSQL批量装载已执行；生产Supabase迁移未执行。
日期：2026年7月10日。
结果：20份报告内容哈希、官方复合原文哈希、确定性投影、引用检查、数据库装载和幂等性均通过。

## 一、目标

把当前20份人工报告迁入不可变修订体系，同时证明迁移前后事实、结构、权威公司范围、前端展示和质量门一致。迁移不借机改写报告正文。

## 二、迁移输入

权威输入为Git仓库中的：

- `manual-reports/*.json`；
- `report-governance-registry-v1.0.json`；
- 从固定官方来源重新取得的网页正文、直接挂载附件、规范化原文和内容哈希；
- 当前生产policy ID与external ID映射。

生产`metadata.reportPayload`只用于迁移对照，不反向覆盖仓库JSON。生产`full_text`同样用于差异核对，不自动覆盖已经验证的官方网页及附件复合原文；若生产文本缺附件或解析范围不同，应记录差异而不是降低目标事实源完整性。

## 三、迁移步骤

1. 建立policy、仓库报告文件和生产记录的一一映射；
2. 对每份JSON执行严格校验并计算规范化`content_hash`；
3. 创建初始draft revision，`change_reason=legacy_baseline_migration`；
4. 记录原文哈希、模式版本和分析版本；
5. 从revision生成全部投影并记录成功投影运行；
6. 使用明确的迁移审核主体将revision置为approved，再事务化发布；
7. 生成迁移对照报告；
8. 在影子读取模式下同时读取旧metadata和新revision；
9. 全部验收通过后再切换当前发布指针和读取入口。

## 四、逐份验收项

每份报告必须满足：

- policy ID、标题、发布机构、日期和来源一致；
- payload规范化前后语义字段无丢失；
- 严格校验结果一致；
- 7个现有章节仍可读取；
- A/B/C类别和full/light状态一致；
- 17份完整报告五模块完整；
- 3份轻量报告保持轻量，不被强制补齐；
- `companyMap`数量、顺序、关系、证据等级和监管角色一致；
- 产业节点、边、政策网络和证据引用无悬空；
- 列表产业数、公司数和证据数由投影计算后与当前权威口径一致；
- 当前生产页面的代表性公司卡数量不发生变化；
- revision payload哈希和投影哈希可复算。

## 五、全量验收门

必须全部通过：

```text
20/20 revision创建成功
20/20 严格校验通过
20/20 投影成功
17/17 完整报告五模块一致
3/3 轻量报告兼容
20/20 companyMap权威计数一致
0 悬空引用
0 未解释字段丢失
0 用户可见正文变化
```

同时运行：

- 全量报告回归测试；
- 治理指标；
- 数据库迁移测试；
- 修订读取与旧读取差异测试；
- 桌面和移动端认证态抽查；
- 发布与回滚演练；
- 备份恢复验证。

## 六、差异分类

迁移差异分为：

- **允许的技术差异：** 字段顺序、规范化空值、派生计数不再重复存储、兼容别名收敛；
- **需人工确认：** 当前metadata与仓库JSON不一致、原文哈希缺失、历史ID无法一一映射；
- **禁止差异：** 报告结论、公司关系、证据摘录、风险边界、政策网络含义发生变化。

发现禁止差异时停止该报告迁移，不为完成20/20而自动修正正文。

## 八、切换与回滚

切换前保留旧读取路径。新路径连续完成：

- 全量契约测试；
- 至少一次生产影子读取；
- 一次完整发布演练；
- 一次历史版本回滚演练；
- 一次真实Supabase暂存迁移和RLS/PostgREST验收；
- 一次生产备份与恢复点验证。

切换失败时仅回退读取指针和API路由，不删除已创建revision。旧metadata在阶段十三前保持只读兼容，稳定后再清理。
